## 상위 근거

**DAT-002 — 주문·체결 로그 OrderLog**

**REQ-002 — 실전 주문 사용자 '실행' 확인 필수**
**NTE-001 — 실전 주문 안전장치: AI는 출사표(주문 초안)만, 실행은 사람이**
**한 줄 요약: AI는 주문 제안서(출사표)까지만 만들고, 실제 돈이 나가는 주문은 사람이 '실행' 버튼을 눌러야만 나간다.** (전문: `octet context NTE-001`)
**한 줄 요약: 실전 주문은 사람이 '실행'을 확인한 경우에만 증권사로 나간다 — AI 단독 주문은 구조적으로 불가능해야 한다.**
실전 계좌는 진짜 돈이 움직인다. AI가 오작동해도 돈이 나가지 않도록, 사람의 확인을 주문 전송의 필수 관문으로 만든다.
실전 주문은 사용자 확인 플래그(사람이 '실행'을 눌렀다는 표시)가 있는 경우에만 증권사 API로 전송되며, 플래그가 없으면 전송 직전 단계(클라이언트)에서 차단된다.

## 시스템 모듈 구조

**한 줄 요약(결정안): 저장소는 지금처럼 파일(md·jsonl) + Git을 유지한다 — DB 서버 없이, 사람이 읽을 수 있고 Git으로 추적되는 장부.**

| 비교 | A. 파일(md·jsonl) + Git (선택안) | B. SQLite |
|---|---|---|
| 의존성 | 0(텍스트 파일) | 드라이버 필요(그래도 가벼움) |
| 기존 자산 | 현행 장부(md·jsonl) 그대로 | 이관 작업 필요 |
| 사람이 직접 읽기 | 가능(에디터로 열림) | 도구 필요 |
| 이력 추적 | Git diff로 공짜 | 별도 구현 필요 |
| 집계 성능 | 느릴 수 있음(전체 스캔) | 빠름(인덱스) |
| 동시 쓰기 | 단일 데몬이라 문제 적음 | 강함 |

선택 이유: 단일 사용자·단일 데몬 구조에서는 파일의 약점(동시성·집계)이 거의 드러나지 않고, Git-native 이력·zero-dependency·기존 장부 호환이 모두 A의 압도적 장점이다.

## 데이터 흐름 (Data Flow)

- 원장류(추가 전용): `order_log`·`violation`·`rule_change`·`captive_ledger` → **jsonl**(1행=1이벤트, [[DAT-002]]·[[DAT-010]]·[[DAT-011]]·[[DAT-012]]).
- 상태류(현재 값): `guard_config`·`nation_ledger`·`general_rank`·`watchlist` → **json/md**(덮어쓰기, 변경은 Git 커밋).
- 집계(논공행상·포로 합계)는 데몬이 jsonl을 스캔해 계산하고, 필요 시 일일 캐시 파일로 저장.

## 인프라/의존성

- 디렉터리 구조와 파일 포맷은 DAT 12건의 스키마를 그대로 따른다(필드명 동일).
- Git 저장소에 커밋(문서·장부). 단, **증권사 키·토큰 파일은 .gitignore로 절대 제외**(RISK-001).

## 보안 및 인증

- 장부 파일에는 금액·종목만 있고 키·계좌번호 전문은 저장하지 않는다.

## 위험

- 데이터가 수년치로 쌓이면 jsonl 전체 스캔 집계가 느려질 수 있다. 완화: 월별 파일 분할 + 일일 집계 캐시.
- 파일 수동 편집으로 정합성 깨짐. 완화: 데몬 기동 시 정합성 검사(장부 합계 재계산).

## 확정 (군주 결정 반영, 2026-11-24)

1. **SQLite 도입 기준 확정**: 원장(jsonl)이 1만 행을 초과하거나 집계가 3초를 초과하면, 그때 SQLite를 **'집계 캐시'로만** 도입한다. 원본(진실의 원천)은 계속 파일(md·jsonl)+Git이다.
