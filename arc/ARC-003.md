## 상위 근거

**SCR-001 — 출사표 확인·실행 모달**

**DAT-001 — 출사표 OrderDraft**
**REQ-001 — 출사표 필수 5항목 검증**
**NTE-001 — 실전 주문 안전장치: AI는 출사표(주문 초안)만, 실행은 사람이**
**한 줄 요약: AI는 주문 제안서(출사표)까지만 만들고, 실제 돈이 나가는 주문은 사람이 '실행' 버튼을 눌러야만 나간다.** (전문: `octet context NTE-001`)
**한 줄 요약: 출사표(주문 초안)는 5가지 항목이 모두 채워져야만 성립한다.**
출사표는 모든 주문의 출발점이다. 항목이 빠진 채 주문이 나가면 손절선 없는 매매 같은 사고로 이어지므로, 성립 요건을 시스템이 강제한다.

## 시스템 모듈 구조

**한 줄 요약(결정안): 증권사 호출은 KIS 어댑터(kis_client.js 계승) 하나로, 주문은 단일 게이트 함수 하나로만 나간다 — 게이트를 거치지 않는 주문 경로는 코드상 존재하지 않는다.**

| 비교 | A. 단일 주문 게이트 (선택안) | B. 화면·루틴별 직접 호출 |
|---|---|---|
| 안전장치 보장 | 검사를 빠뜨릴 수 없음(한 문) | 경로마다 검사 누락 위험 |
| 감사 추적 | 게이트에서 전 건 로그 | 흩어짐 |
| 구현 비용 | 게이트 1개 구현 | 당장은 쉬우나 위험 누적 |

선택 이유: REQ-001~004·015의 겹겹 안전장치는 "모든 주문이 한 문을 통과"할 때만 보장된다. RISK-004(과매매·중복 주문)의 구조적 해법.

- 모듈: `kis-adapter`(현행 kis_client.js 계승 — 토큰 캐시, 호출 간 1.2초 간격, 재시도) / `order-gate`(검사 파이프라인) / `order-logger`(jsonl 기록).

## 데이터 흐름 (Data Flow)

게이트 검사 순서(모두 통과해야 전송, 하나라도 걸리면 blocked 기록):

1. STOP 파일 존재([[REQ-004]]) → 2. 출사표 성립 5항목([[REQ-001]]) → 3. 사용자 확인 플래그 — 실전만([[REQ-002]]) → 4. 화이트리스트·지정가 — 실전 매수([[REQ-004]]) → 5. 1회 한도·하루 손실([[REQ-003]]) → 6. 군령 3종: 군량 30%·복수 매매·상관 0.7([[REQ-015]]) → 7. 관직 한도([[DAT-011]]) → KIS 어댑터 전송 → 체결조회 → `order_log` 기록([[DAT-002]]).

차단 시: `status=blocked` + `block_reason`을 order_log에 기록하고 화면([[SCR-001]])에 사유·수치 반환.

## 인프라/의존성

- 현행 kis_client.js의 검증된 부분(토큰 캐시·1.2초 간격·jsonl 로그)을 그대로 계승. guard.json 한도는 [[DAT-003]](guard_config)으로 통합.
- 모의/실전은 같은 게이트, 다른 KIS 도메인 — 분기는 어댑터 안에서만.

## 보안 및 인증

- KIS 토큰은 메모리+로컬 캐시 파일(키 관리는 [[ARC-005]]). 어댑터 밖으로 토큰·키를 넘기지 않는다.
- 사용자 확인 플래그는 게이트가 전송 직전 재검사(이중 검사 — [[REQ-002]]).

## 위험

- **실전 주문 TR 미검증(RISK-002)**: 모의와 실전의 전문 차이로 첫 실전 주문 실패 가능. 완화: 첫 출병 최소 수량 + 체결조회 확인 + 실패 시 수동 HTS.
- KIS 측 장애·토큰 만료 연쇄: 어댑터에서 재발급 1회 재시도 후 실패 보고(무한 재시도 금지).

## 확정 (군주 결정 반영, 2026-11-24)

1. **실전 TR 첫 검증은 엘티씨 첫 실전 출병이 겸한다** — 별도 검증 출병을 만들지 않고, 최소 수량·체결조회 확인·실패 시 수동 HTS 원칙(RISK-002 대응)을 그대로 적용한다.
2. **체결조회 주기**: 주문 직후 10초 간격으로 최대 1분간 확인하고, 이후에는 척후 5분 주기([[REQ-006]])에 포함해 확인한다.
