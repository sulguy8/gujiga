## 시스템 모듈 구조

**한 줄 요약(결정안): 당분간 정시 작업(08:31·5분·15:05)은 검증된 Aside 루틴이 계속 맡고, 앱 데몬은 결과 수신·기록만 한다. 앱이 안정되면 데몬 내장 cron으로 한 번에 이관한다(2중 실행 금지).**

| 비교 | A. Aside 루틴 유지→후일 이관 (선택안) | B. 즉시 데몬 cron 전환 |
|---|---|---|
| 안정성 | 이미 실운용 검증됨 | 새 구현 초기 버그 위험 |
| 중복 실행 위험 | 이관 규칙만 지키면 낮음 | 전환기에 2중 실행 위험 |
| 의존성 | Aside에 계속 의존 | 앱 단독 완결 |
| 전환 비용 | 나중에 1회 | 지금 즉시 |

선택 이유: 정시 루틴은 돈이 걸린 경로라 "돌아가는 것"이 최우선. RISK-004의 교훈(같은 루틴 중복 실행 금지)에 따라 **이관 시 반드시 원본 루틴을 먼저 삭제한 뒤 새 쪽을 켠다** — 두 곳에서 같은 시각 작업이 도는 기간을 0으로.

## 데이터 흐름 (Data Flow)

- 이행기: Aside 루틴(08:31 브리핑 / 5분 정찰 / 15:05 점검) → 결과를 앱 장부·알림으로 전달 → 앱 화면([[SCR-002]]~[[SCR-004]])이 표시.
- 이관 후: 데몬 내장 cron이 같은 시각표로 동일 작업 실행. 거래일 캘린더·08:30 주문 접수 제약([[REQ-005]])은 공통 모듈로.
- 모든 정시 작업은 실행 기록(시각·성공 여부)을 남겨 "미실행 감지"가 가능해야 한다.

## 인프라/의존성

- 이행기에는 Aside 가동이 전제(회사 PC). 경로는 절대 경로 한 곳만 참조(RISK-003 재발 방지 — u0→u1 사고).
- 이관 단위는 루틴 1개씩(브리핑부터)이 아니라 **시각대 단위로 한 번에** — 반쪽 이관이 가장 위험.

## 보안 및 인증

- 루틴이 생성하는 것은 출사표·알림까지. 실전 전송은 게이트([[ARC-003]])의 사용자 확인을 반드시 거친다.

## 위험

- 이관 중 중복 실행(양쪽 모두 가동) → 중복 출사표·중복 알림(RISK-004). 완화: 원본 삭제 선행 + 데몬이 같은 시각 작업의 중복 기록을 감지하면 경고.
- Aside 의존 기간 중 Aside 장애 시 루틴 공백. 완화: 미실행 감지 알림.

## 확정 (군주 결정 반영, 2026-11-24)

1. **이관 시점**: Aside 루틴을 유지하다가, 앱 데몬이 **모의 2주 무사고**를 달성하면 이관을 시작한다.
2. **이관 방식**: 시간대별(08:31 / 5분 정찰 / 15:05)로 순차 이관하되, 같은 시간대는 반쪽 금지. **이관 시 원본 루틴을 먼저 삭제한 뒤** 데몬 cron을 켠다(중복 실행 0 — RISK-004).
