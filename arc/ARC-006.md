## 시스템 모듈 구조

**한 줄 요약(결정안): PC(회사)는 OS 알림으로 확정, 휴대폰 도달 채널은 메신저 봇 vs PWA 푸시 중 군주 결정 대기 — 알림 발송은 데몬의 notify 모듈 한 곳으로 통일한다.**

| 비교(모바일 채널) | A. 메신저 봇(예: 텔레그램) | B. PWA 웹푸시 |
|---|---|---|
| 서버 필요 | 불필요(봇 API 직접 호출) | 푸시 서버 경유 필요 — 로컬 데몬 구조(ARC-001)와 상성 나쁨 |
| 구현 난도 | 낮음(HTTP 1회) | 높음(서비스워커+푸시 구독 관리) |
| 의존성 | 외부 메신저 1개 | 브라우저 푸시 인프라 |
| 보는 곳 | 메신저 앱 | 설치한 PWA |
| 민감정보 | 외부 서비스에 알림 본문 전송됨 | 상대적으로 적음 |

- notify 모듈: 발신처는 1곳(브리핑·척후·점검·차단 알림 전부 여기로). 채널(OS/메신저)은 설정으로 켜고 끈다.

## 데이터 흐름 (Data Flow)

정시 루틴·게이트 → notify 모듈 → ① PC: OS 알림(클릭 시 해당 화면 딥링크 — [[SCR-002]]~[[SCR-004]]) ② 모바일: 선택된 채널로 요약 1줄 + 앱 링크. 알림 원문은 로컬 장부에 기록(채널은 전달만).

## 인프라/의존성

- OS 알림은 추가 의존성 0. 메신저 봇 선택 시 해당 API 토큰 1개가 추가 비밀 정보가 된다([[ARC-005]] 관리 대상에 포함).

## 보안 및 인증

- 메신저 채널 사용 시 **알림 본문에 금액·계좌 정보 최소화**(종목·조건명 수준) — 외부 서버를 거치기 때문.
- 봇 토큰도 키 파일과 동일한 보관 규칙(git 금지, 암호화 범위 포함).

## 위험

- 모바일 채널 미정 상태가 길어지면 장중 긴급 알림(성벽 접근·차단)을 밖에서 못 받는다 — 정시 루틴의 가치 반감.
- 메신저 의존 시 해당 서비스 장애가 알림 공백으로 직결. 완화: PC OS 알림은 항상 병행.

## 미결 (군주 결정 필요)

1. **모바일 채널 선택**: 메신저 봇(잠정 우세 — 서버 불필요·구현 쉬움) vs PWA 푸시 vs 당분간 PC 알림만.
2. 메신저 선택 시 어느 메신저로 할지와 알림 본문 수위(금액 포함 여부).
