## 상위 근거

**TSK-024 — 매수 체결 자동 반영: 그림자 watchSorties·관문 기록 확장**

**한 줄 요약: 걸어둔 매수 주문(매복)이 나중에 체결되면 자동으로 장부(order_log)와 보유 목록(positions)에 올라가는지 검증한다.**

## 사전 환경 조건

- **검증 대상**: [[TSK-024]] gate.submit 기록 확장 + 그림자 watchSorties.
- 사전 조건: 가짜 provider(실서버 호출 없이 체결조회 응답을 흉내내는 테스트용 모듈)로 fills(모의)·fillsReal(실전) 응답을 주입. 임시 데이터 폴더(order_log·positions·shadow_job_log 초기화).
- **실행 방법: 자동(테스트 코드)** — 실서버 호출 0건. 테스트 코드 먼저 작성(실패 확인) 후 구현.

## 검증 시나리오 (Pass/Fail)

| # | 입력 | 기대 결과 |
|---|---|---|
| 1 | 모의 매수 submitted 행 + 전량 체결(remain=0) 응답 | order_log에 filled 행, positions에 open 행 추가 — 출사표 필드(stop_price·target_price·deadline·hypothesis_ids)가 submitted 행에서 복원됨 |
| 2 | 1 직후 watchSorties 재실행(같은 체결 응답) | 쓰기 0건(멱등 — 주문번호 기준) |
| 3 | pollFill이 이미 filled를 기록한 주문의 체결 응답 | order_log 추가 생략, positions만 보충(open 행 1건) |
| 4 | 부분 체결(remain>0) 응답 | order_log·positions 불변, note만 기록 |
| 5 | submitted 행 없는 체결 응답(관문 밖 주문) | 장부 반영 0건, shadow_job_log에 note 기록 |
| 6 | 실전(fillsReal) 전량 체결 응답 | 1·2와 동일 동작 |
| 7 | 회군(매도) 체결이 섞인 응답 | watchSorties는 매수만 처리, 기존 watchRetreats 테스트 전부 통과(간섭 없음) |
| 8 | 전 시나리오 통틀어 가짜 provider 기록 검사 | 실서버 주문·전송 호출 0건(조회만) |

## 경계값/에지 케이스

- 같은 종목을 다른 주문번호로 2건 체결: positions에 2행(주문번호별 분리) — 종목명 기준 중복 제거를 하지 않는지 확인.
- 모의 체결 반영 후 nation.saveLedger 호출로 세력 장부 스냅샷 갱신([[REQ-009]] — 체결은 전부 한 나라에 귀속).
- 체결 응답에 매수·매도·부분이 한꺼번에 섞여도 각자 규칙대로 처리.
